# Lambda-only cutover: production hold

**Do not merge to `main` or apply until the preflight below passes.** Merging the workflow changes can trigger a Lambda deployment and the existing Neon schema push. This is a static audit, not a live inventory or a Terraform plan.

## State and destruction audit

**Intended physical destroys in this change: none.** If present in state, `removed` with `destroy = false` forgets the legacy module and SSM interface endpoint without deleting them. They remain live, billable, and unmanaged after that operation. Terraform will not automatically restore management on a Git revert. Record owners, original addresses, resource IDs and a protected state recovery point before handoff; arrange adoption by a dedicated retirement stack or an approved import/recovery procedure. Keep the random provider during this handoff for the old state.

The production API module stays at `module.hono_serverless_api[0]`; all child addresses, API hostname, Gateway mapping, Lambda names, and both receipt Lambda addresses stay unchanged. The root API alias and receipt queue mapping keep their addresses but now target the Gateway and Neon processor respectively. If they already do, neither should change. The shared GitHub role and policy stay at their existing addresses; only legacy deploy grants (ECR, ECS, EC2 describe and PassRole) are removed. Keep the legacy RDS processor, its IAM/logs, VPC/subnets/routes/security groups and S3 endpoint for rollback. The receipt S3 bucket and notification, queue/DLQ, frontend bucket/CloudFront/TLS/DNS, hosted zone, Terraform-state bucket, shared SSM parameters and Neon database are not removed. The externally provisioned Neon connection and Anthropic SSM entries remain prerequisites, not deletion targets.

## Rollout gates (authorized operator only)

1. Inventory production state, API alias target, Gateway custom hostname/TLS/mapping, queue mapping target and status, legacy consumers, and app configuration. Confirm the shared deploy role has no remaining external consumers of the retired permissions. Protect state backups as sensitive. Remove stale mode inputs from operator configuration; no GitHub settings change is needed for code to ignore the old variable.
2. If API Gateway and the Neon processor are already live, verify `/health`, login/logout/session and organization membership, browser/extension credentials and CORS, chat, and a receipt upload through S3, SQS and Neon to the UI. Inspect queue backlog, DLQ, errors and latency. Review a separately authorized production plan with the expected artifact versions: see [ADR 002](adr/002-lambda-deployment-ownership.md) for code drift. Reject any destroy or replacement, unexpected creation, routing change, schema change, or code rollback. Verify the proposed Neon schema changes separately before the workflow runs.
3. If either target is still legacy, **stop**: stage the Gateway and Neon processor without moving production DNS or adding a second consumer to the same queue. Audit ACM DNS validation record ownership; both certificates can use the same CNAME, so adopt a single owner instead of blindly creating/deleting the record. Rehearse backup/restore and reconcile RDS to Neon (auth/users/sessions/orgs, receipts/jobs, chat/checkpoints); validate schema, keys and counts. Agree on a write freeze or tested delta sync. Exercise the new path on isolated traffic and a test queue first. During the approved cutover, pause writes/uploads, drain or reconcile in-flight jobs, change the single consumer and API alias together, verify on the existing hostname, then resume. Keep prior DNS and mapping targets and a data reconciliation/rollback procedure; once Neon accepts writes, pointing back to RDS alone is not a safe rollback.
4. Only after a monitored rollback window and explicit ownership approval, plan a **separate** decommission. Retire ECS service/tasks/cluster, ALB/listeners/target group, unused ECS roles/rules, and ECR/logs after retention checks. Retire the RDS processor, its endpoint and networking only after confirming zero remaining users. Keep RDS and its parameter until an owner signs off on a tested restore and retention; the old RDS definition has `skip_final_snapshot = true`, so never use its original deletion settings as a backup strategy. Never delete an ACM validation CNAME still used for renewal or any shared bucket, queue, DNS zone or IAM/SSM dependency. No such deletion is implemented here.
